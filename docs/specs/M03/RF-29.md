# RF-29 · Transición entre nodos conversacionales

- **Versión del RF que se implementa:** 1.1 (hoja «M03 - Chat» del Excel, descargado el 2026-11-07)
- **Módulo / feature:** M03 · `chat`
- **Rol(es) que lo usan:** ESTUDIANTE (el actor del RF es el sistema; la interfaz presenta el resultado)
- **Ruta(s):** `/app/estudiante/chat`
- **Contrato de API:** Taiga #250. La transición la decide el backend en el mismo `POST /chat/sesiones/{idSesion}/respuestas` de RF-27.
- **Dependencias:** RF-25 (reglas de transición), RF-28 (respuesta válida), RF-26 (presentar el nodo destino)

## Contrato de API

Éxito, 200:

```json
{
  "idRespuesta": "uuid",
  "resultado": "VALIDA",
  "transicion": {
    "idNodoOrigen": "uuid",
    "idNodoDestino": "uuid",
    "esTerminal": false
  },
  "estadoSesion": "ACTIVA"
}
```

- `estadoSesion` es `ACTIVA` o `COMPLETADA`. Si el destino es terminal, `esTerminal` es `true`.
- La respuesta **no** trae el contenido del nodo destino: se obtiene con `GET /chat/sesiones/{idSesion}/nodo-actual` (RF-26).
- Reenviar el mismo `idRespuesta` devuelve este mismo cuerpo.

Errores de transición, cuerpo `{ "statusCode", "codigo", "mensaje", "campo" }`:

| HTTP | `codigo` | Cuándo |
|---|---|---|
| 500 | `SIN_TRANSICION` | Ninguna regla coincide con la respuesta |
| 500 | `DESTINO_INVALIDO` | El nodo destino no pertenece al flujo de la sesión (defensivo) |
| 500 | `ERROR_PERFIL` | No se pudo leer el perfil para evaluar la regla |

## Comportamiento esperado

1. La interfaz no elige el siguiente nodo ni evalúa reglas: muestra el destino que decidió el backend.
2. Tras un 200, la respuesta enviada queda en la conversación y se presenta el nodo destino obtenido con RF-26.
3. Hay una sola transición por respuesta. Mientras se carga el destino no se puede responder de nuevo.
4. Si `estadoSesion` es `COMPLETADA`, la conversación termina y no se ofrecen más respuestas (contenido final pendiente de A-016).
5. Ante un error de transición se muestra el `mensaje` del backend; la estudiante permanece en el nodo actual y puede reintentar con el mismo `idRespuesta`.
6. La transición no modifica la respuesta enviada.

## Criterios de aceptación

- **CA-29-1.** Dado un 200 con `estadoSesion: "ACTIVA"`, cuando llega, entonces se pide el nodo actual y se presenta el nodo destino.
- **CA-29-2.** Dado un 200, cuando se presenta el destino, entonces la respuesta enviada sigue visible en la conversación sin cambios.
- **CA-29-3.** Dado un 200 con `estadoSesion: "COMPLETADA"`, cuando llega, entonces no se ofrece ningún componente de respuesta.
- **CA-29-4.** Dado un 500 `SIN_TRANSICION`, `DESTINO_INVALIDO` o `ERROR_PERFIL`, cuando llega, entonces se muestra el `mensaje` del backend tal cual, el nodo actual sigue visible y se puede reintentar.
- **CA-29-5.** Dado un reintento tras un 5xx, cuando se envía, entonces lleva el mismo `idRespuesta`, y si el backend ya la había procesado se sigue con el mismo destino.
- **CA-29-6.** Dado un 200, cuando la interfaz avanza, entonces no hizo ningún cálculo de reglas: el nodo presentado es el que devuelve RF-26.

## Estados de interfaz

- **Avanzando:** esqueleto de carga mientras llega el nodo destino.
- **Éxito:** nodo destino presentado (RF-26).
- **Conversación completada:** sin componente de respuesta (A-016).
- **Error por `codigo`:** `SIN_TRANSICION`, `DESTINO_INVALIDO`, `ERROR_PERFIL`: mensaje del backend y reintentar.

## Textos normativos

Del Excel; el backend los envía en `mensaje` y se muestran VERBATIM:

- Sin regla de transición válida: «No se pudo determinar la siguiente acción en la conversación.»
- Nodo destino inválido: «El nodo destino no es válido.»

RF-29 v1.1 eliminó «Respuesta no validada» (400): validación y transición ocurren en la misma petición y los rechazos llegan con los mensajes de RF-28.
