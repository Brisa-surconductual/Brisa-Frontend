# RF-25 · Gestión del árbol conversacional (modalidad grupal)

- **Versión del RF que se implementa:** 1.1 (hoja M03 del Excel)
- **Módulo / feature:** M03 · `chat`
- **Rol(es) que lo usan:** ADMINISTRATIVO
- **Ruta:** `/app/administrativo/chat/grupal`
- **Contrato de API:** JSON real del backend, rutas `/chat/admin/...` (se usan estas y no las históricas `/chat/administracion/...`).
- **Dependencias:** RF-25B (modalidad), RF-25C (árboles personalizados, otra pantalla)

## Alcance por entregas

El RF pide definir y gestionar nodos, transiciones y reglas. Se entrega en PR pequeños:

| PR | Contenido | Estado |
|---|---|---|
| 1 | Listar flujos grupales, filtrar por estado, crear borrador, catálogos | Hecho |
| 2 | Vista del árbol (nodos y transiciones), solo lectura | Hecho |
| 3 | Crear y editar nodos | Hecho |
| 4 | Transiciones y reglas de validación | Pendiente |
| 5 | Publicar y archivar | Hecho (parcial: validar explícito y clonar versión siguen pendientes) |

## PR 1 · Comportamiento esperado

1. Al entrar se consulta `GET /chat/admin/flujos?modalidad=GRUPAL&page=1&page_size=10` y se listan los flujos con nombre, estado (texto e ícono), versión y fecha.
2. El filtro de estado usa `enums.estado_flujo` de `GET /chat/admin/catalogos`; si el catálogo falla, usa BORRADOR, PUBLICADO y ARCHIVADO.
3. Si hay más de una página, hay paginación anterior y siguiente.
4. El formulario crea un flujo con `POST /chat/admin/flujos` y cuerpo `{ nombre, modalidad: "GRUPAL" }`. No se envía perfil clínico: el backend lo rechaza para GRUPAL.
5. El nombre es obligatorio y de hasta 150 caracteres; el error se muestra como texto.
6. Al crear, el nuevo borrador aparece en el listado (primera página, sin filtro) y se muestra un aviso con su versión.
7. Los mensajes de error del backend se muestran tal cual.

## PR 1 · Criterios de aceptación

- **CA-25-1.** Dado un administrador, cuando abre `/app/administrativo/chat/grupal`, entonces ve «Consultando flujos...» y luego la lista de flujos grupales.
- **CA-25-2.** Dado un flujo PUBLICADO y uno BORRADOR, entonces cada uno muestra su estado con texto («Publicado», «Borrador») además del color.
- **CA-25-3.** Dado un filtro de estado, entonces se vuelve a consultar con ese `estado` desde la página 1.
- **CA-25-4.** Dada una respuesta sin flujos, entonces se invita a crear el primero (o se dice que no hay con ese estado).
- **CA-25-5.** Dado un nombre vacío o de más de 150 caracteres, entonces no se llama al backend y se muestra el error junto al campo.
- **CA-25-6.** Dado un nombre válido, entonces se envía solo `nombre` y `modalidad: "GRUPAL"` y el listado se recarga con el borrador nuevo.
- **CA-25-7.** Dado un error del backend al listar o al crear, entonces se muestra su mensaje; al listar hay botón «Reintentar».

## PR 2 · Vista del árbol

- **Ruta:** `/app/administrativo/chat/grupal/:flowId`, desde «Ver árbol» en cada flujo del listado.
- **Endpoint:** `GET /chat/admin/flujos/:id_flujo` → `{ "data": { "flujo": Flujo, "nodos": [Nodo], "transiciones": [Transicion] } }`.
- `Nodo`: `id_nodo`, `id_flujo`, `id_tipo_nodo`, `tipo_nodo`, `contenido` (objeto; el texto va en `contenido.texto`), `es_nodo_inicial`, `orden` (puede ser null), `id_contenido_cronograma`, `creado_por`, `fecha_creacion`, `fecha_actualizacion`.
- `Transicion` (versión admin): `id_regla` (**es el id de la transición**), `id_flujo`, `id_nodo_origen`, `id_nodo_destino`, `id_regla_validacion`, `operador_condicion` (IGUALDAD, RANGO o CATEGORIA), `valor_condicion` (objeto libre), `orden_evaluacion`, `fecha_creacion`.

Comportamiento:

1. Muestra el nombre, la versión y el estado del flujo (texto e ícono).
2. Lista los nodos con el inicial primero, luego por `orden` (sin orden al final). El texto se muestra tal cual.
3. Lista las transiciones por `orden_evaluacion`, con el nombre del nodo de origen y de destino, el operador y la condición.
4. La condición se muestra como `clave: valor` sin asumir un formato propio (el backend la envía como objeto libre).
5. Es de solo lectura.

Criterios de aceptación:

- **CA-25-8.** Dado un flujo con nodos y transiciones, entonces se ven ambos listados, con el nodo inicial marcado «Nodo inicial».
- **CA-25-9.** Dado un nodo sin `contenido.texto`, entonces se muestra «Sin texto.»; no se inventa contenido.
- **CA-25-10.** Dado un flujo sin nodos o sin transiciones, entonces se dice que aún no tiene.
- **CA-25-11.** Dado un error del backend (por ejemplo, flujo inexistente), entonces se muestra su mensaje y «Reintentar».
- **CA-25-12.** Desde el detalle se puede volver al listado, y la pestaña «Árbol grupal» sigue activa.

## PR 3 · Crear y editar nodos

- **Crear:** `POST /chat/admin/flujos/:id_flujo/nodos` con `{ id_tipo_nodo, contenido, es_nodo_inicial, orden? }` → `{ "data": Nodo }`.
- **Editar:** `PATCH /chat/admin/nodos/:id_nodo` con solo los campos que cambian → `{ "data": Nodo }`. Un cuerpo vacío lo rechaza el backend.
- Solo un flujo en BORRADOR se edita; en otros estados la interfaz no ofrece los botones y el backend rechazaría el cambio.

Comportamiento:

1. En un borrador, «Agregar nodo» abre el formulario y cada nodo tiene «Editar».
2. El formulario pide tipo de nodo (opciones de `tipos_nodo` del catálogo), texto, orden opcional y si es el nodo inicial.
3. El texto es obligatorio; el orden, si se escribe, es un entero desde 1. Los errores se muestran como texto junto al campo.
4. Al crear se envía `contenido: { texto }`. Al editar, `contenido` conserva las demás claves que ya tenía el nodo y solo cambia `texto`.
5. Al editar solo viajan los campos modificados; si no hay cambios, se avisa sin llamar al backend.
6. Los errores del backend se muestran tal cual y el formulario conserva lo escrito.
7. Al guardar se cierra el formulario, se avisa y se vuelve a consultar el árbol.

Criterios de aceptación:

- **CA-25-13.** Dado un flujo PUBLICADO o ARCHIVADO, entonces no hay «Agregar nodo» ni «Editar».
- **CA-25-14.** Dado un texto vacío, un tipo sin elegir o un orden no entero, entonces no se llama al backend y cada error aparece junto a su campo.
- **CA-25-15.** Dado un nodo nuevo válido, entonces se envía `{ id_tipo_nodo, contenido: { texto }, es_nodo_inicial }` (y `orden` solo si se escribió).
- **CA-25-16.** Dada una edición, entonces el PATCH lleva solo lo que cambió y conserva las otras claves de `contenido`.
- **CA-25-17.** Dado un error del backend (por ejemplo, ya existe un nodo inicial), entonces se muestra su mensaje y no se pierde lo escrito.

## PR 5 (parcial) · Publicar y archivar

- **Publicar:** `POST /chat/admin/flujos/:id_flujo/publicar`, cuerpo `{}` → `{ "data": { id_flujo, estado, version, fecha_publicacion } }`. Solo un BORRADOR puede publicarse; el backend valida la estructura del árbol (nodo inicial, huérfanos, ciclos) antes de publicar y responde `422 GRAFO_INVALIDO` si no es válida, o `409 ESTADO_INVALIDO`/`409 FLUJO_GRUPAL_PUBLICADO_EXISTENTE` según el caso.
- **Archivar:** `POST /chat/admin/flujos/:id_flujo/archivar`, cuerpo `{}` → `{ "data": { id_flujo, estado, fecha_archivado } }`. Funciona desde BORRADOR o PUBLICADO; un flujo ya archivado responde `409 ESTADO_INVALIDO`.
- No existe "despublicar" ni "desarchivar": el ciclo de vida no vuelve atrás. Para una versión nueva de un flujo publicado o archivado, el camino es `POST /chat/admin/flujos/:id_flujo/clonar-version` (fuera de este PR).

Comportamiento:

1. En el detalle del flujo (`/app/administrativo/chat/grupal/:flowId`), un BORRADOR ofrece «Publicar» y «Archivar»; un PUBLICADO ofrece solo «Archivar»; un ARCHIVADO no ofrece ninguna acción.
2. Ambas acciones piden confirmación antes de ejecutarse (mismo patrón que RF-25C en `PersonalizedTreesPage`).
3. Al confirmar, se llama al backend; al terminar se cierra la confirmación, se avisa con un mensaje fijo del frontend («Flujo publicado.» / «Flujo archivado.») y se vuelve a consultar el árbol para reflejar el nuevo estado y la fecha.
4. Un error del backend (por ejemplo, `422 GRAFO_INVALIDO` o `409 ESTADO_INVALIDO`) se muestra tal cual, sin cerrar el diálogo de confirmación de forma silenciosa ni perder el árbol ya cargado.
5. La interfaz no llama a `POST /chat/admin/flujos/:id_flujo/validar` por separado: `publicar` ya valida la estructura y devuelve el detalle en el 422.

Criterios de aceptación:

- **CA-25-18.** Dado un flujo BORRADOR, entonces el detalle ofrece «Publicar» y «Archivar».
- **CA-25-19.** Dado un flujo PUBLICADO, entonces el detalle ofrece solo «Archivar» (nunca «Publicar» ni una opción de despublicar).
- **CA-25-20.** Dado un flujo ARCHIVADO, entonces el detalle no ofrece ninguna acción de cambio de estado.
- **CA-25-21.** Dada cualquiera de las dos acciones, entonces se pide confirmación antes de llamar al backend.
- **CA-25-22.** Dada una confirmación exitosa, entonces se avisa, se recarga el árbol y el badge de estado refleja el cambio.
- **CA-25-23.** Dado un error del backend al publicar o archivar (por ejemplo, árbol inválido o estado que ya no lo permite), entonces se muestra su mensaje en una zona propia, sin perder el árbol visible.

Fuera de alcance de este PR: `POST /chat/admin/flujos/:id_flujo/validar` como acción independiente (la interfaz no la expone) y `POST /chat/admin/flujos/:id_flujo/clonar-version` (nueva versión de un flujo publicado o archivado).

## JSON real del backend

- `GET /chat/admin/flujos` → `{ "data": { "items": [Flujo] }, "meta": { "page", "page_size", "total" } }` (sin envoltorio extra). Query: `modalidad`, `estado`, `page` (≥1), `page_size` (1 a 100).
- `POST /chat/admin/flujos` → `{ "data": Flujo }`. Body: `{ nombre (≤150), modalidad }`; el perfil clínico solo aplica a PERSONALIZADA.
- `GET /chat/admin/catalogos` → `{ "data": { tipos_nodo, tipos_entrada, reglas_validacion, enums: { modalidad, tipo_dependencia, tipo_craving, operador_condicion, tipo_dato, estado_flujo } } }`.
- `Flujo`: `id_flujo`, `nombre`, `modalidad`, `estado`, `version`, `creado_por`, `fecha_creacion`, `fecha_publicacion`, `tipo_dependencia`, `tipo_craving`, `fecha_archivado`.
- `POST /chat/admin/flujos/:id_flujo/publicar` → `{ "data": { id_flujo, estado, version, fecha_publicacion } }`. Errores: `404 FLUJO_CONVERSACIONAL_NO_ENCONTRADO`, `422 GRAFO_INVALIDO` (con `detalles: { sin_nodo_inicial, nodos_huerfanos, ciclos }`), `409 FLUJO_GRUPAL_PUBLICADO_EXISTENTE`.
- `POST /chat/admin/flujos/:id_flujo/archivar` → `{ "data": { id_flujo, estado, fecha_archivado } }`. Errores: `404 FLUJO_CONVERSACIONAL_NO_ENCONTRADO`, `409 ESTADO_INVALIDO` (ya archivado).
- Los métodos que modifican estado exigen sesión ADMINISTRATIVO y `X-CSRF-Token` (lo agrega `apiClient`).

## Fuera de alcance de este PR

Transiciones y reglas, validar como acción independiente y clonar versión. El contenido propio de las preguntas (entrada y reglas de respuesta) no se edita todavía (A-010). Los árboles personalizados (RF-25C) tienen otra pantalla y otro controlador.
